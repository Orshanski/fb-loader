# Нечёткий поиск по библиотеке — дизайн

**Связанные beads:** fb-loader-14x (закрыт, спайк-замеры).

## Цель

Кросс-сущностный fuzzy-поиск по каталогу: одно поле, одна кнопка — на выходе авторы, серии и книги, чьи названия/имена совпали с запросом с поправкой на склонения, опечатки и пунктуацию. Открывается из значка лупы в верхней области сайдбара.

Опорный референс по алгоритму — `~/code/librarium-py/backend/app/search.py` (`token_min_ratio` + `search_preprocess`). Цифры из спайка (`/tmp/fbl-spike/spike.swift`) на реальном кэше пользователя (581k книг / 167k авторов / 69k серий) — типовой запрос отрабатывает за 2.8–3.5 с в одно нажатие, что считаем приемлемым для триггера «по кнопке».

## Архитектура

### Хранилище

In-memory. БД не вводим — это создаст второй персистентный слой параллельно с уже существующим бинарным кэшем `Library`. Поиск всё равно сканирует те же массивы, что уже лежат в RAM, и индекс БД при триггере «по кнопке» не даёт выигрыша по сравнению с честным параллельным проходом.

### Search-ключи

Хранятся как новые транзиентные параллельные массивы внутри `Library` (по тому же паттерну, что существующие `lowercasedAuthorNames`/`lowercasedSeriesNames`):

```swift
let searchKeyAuthors: [[Token]]      // parallel to authors
let searchKeySeries:  [[Token]]      // parallel to series
let searchKeyTitle:   [[Token]]      // parallel to books — only title tokens
let bookAuthorStarts: [UInt32]       // per book + 1: границы в bookAuthorIndices
let bookAuthorIndices: [Int32]       // flat: индексы в searchKeyAuthors всех авторов книги
let searchSeriesIdx:  [Int32]        // per book: index into searchKeySeries, -1 if no series
```

Где `Token` = `[UInt32]` (массив unicode scalar codepoints), не `String`. Скорер работает на raw codepoints, чтобы избежать grapheme-cluster overhead Swift `String`.

**LIGHT-вариант** (выбран по результатам спайка): per-book ключ хранит только токены title; для скоринга книги авторские и серийные токены добираются на лету через `bookAuthorStarts`/`bookAuthorIndices` (все авторы книги, не только первый) и `searchSeriesIdx`. Расширенный ключ серии — имя + токены всех различных авторов всех её книг. Псевдо-автор «(Без автора)» (`Author.unknownID`) в поиске не участвует: пустой ключ, в ключи книг и серий не входит. HEAVY-вариант (хранить уже склеенный книжный ключ) даёт +0.5 с скорости на многословных запросах при сопоставимой памяти, но на бюджете «несколько секунд на клик» эта дельта неразличима для пользователя.

### Когда строится

Синхронно в `Library.init`, сразу после построения существующих вторичных индексов. Это:
- Совпадает с паттерном остальных транзиентных индексов библиотеки.
- Делает любой готовый `Library` поисково-готовым — UI не имеет состояний «индекс ещё не собран».
- Стоит ~2 с на полном каталоге (замерено в спайке).

`Library.init` уже принимает `onStatus` колбэк. В этот канал добавляется сообщение `"Считаем индексы поиска…"` (опционально с процентом) — оно ляжет в существующий `AppState.LoadStage.loading(progress:)` и нарисуется в стандартном лоадере. Пользователь видит «индексы считаем» как часть нормальной загрузки 600k книг.

Не персистится в `LibraryBinaryCodec` — пересборка на каждом запуске стоит ~2 с и идемпотентна; персистенция связала бы on-disk схему с правилами препроцессинга и потребовала бы bump версии формата при любой их корректировке.

### Препроцессинг

Порт `search_preprocess` из `librarium-py`:
0. NFC (только для строк с комбинирующими знаками): «e + U+0301» ≡ «é».
1. ё→е, Ё→Е (rapidfuzz default_process этого не делает).
2. Lowercase любой письменности (посимвольно).
3. Любой не-letter/не-digit codepoint → разделитель токенов.
4. Пустые токены отбрасываются.

Применяется одинаково и к запросу, и к источнику.

### Скорер

Чистый Swift, ~150 строк. Никаких внешних библиотек — `rapidfuzz` Swift-биндингов нет, а `_token_match_score` — bespoke-логика `librarium`, всё равно требует ручного порта.

```swift
func tokenMatchScore(_ q: Token, _ c: Token) -> Double {
    let lcs = lcsLength(q, c)
    let coverage = 100.0 * Double(lcs) / Double(q.count)
    let ratio    = 200.0 * Double(lcs) / Double(q.count + c.count)
    return min(coverage, ratio)
}

func tokenMinRatio(query qTokens: [Token], choice cTokens: [Token]) -> Double {
    // Each query token must find some best-match in choice tokens; the
    // weakest per-token best across the query drags the whole score down.
    qTokens.map { qt in cTokens.map { tokenMatchScore(qt, $0) }.max() ?? 0 }.min() ?? 0
}
```

`lcsLength` — bit-parallel алгоритм Hyyrö'04. Адаптация из `rapidfuzz-cpp/rapidfuzz/distance/LCSseq_impl.hpp` (MIT, © Max Bachmann). Для паттернов длиной ≤ 64 codepoint'а — O(n) с 4-операционным внутренним циклом на одном UInt64-регистре (`u = S & matches; S = (S+u) | (S-u)`). Для редких токенов длиннее 64 символов — fallback на стандартную 1D rolling DP O(m·n).

Корректность бит-парлельной реализации в спайке проверена двумя способами: (а) cross-check `lcsLengthDP(a,b) == lcsLengthBP(a,b)` на всех парах токенов корпуса — все совпали; (б) одинаковые финальные scores у обоих скореров на 13/13 кейсах корпуса.

Однако сам по себе bit-parallel ускорение не даёт — Swift `Dictionary` для pattern-match-vector аллоцируется внутри каждого вызова `lcsLength` (миллионы раз) и хеш-лукапы съедают всю экономию от 4-операционного inner-loop. **Ключевые две оптимизации поверх Hyyrö, которые делают разницу в 6×:**

1. **Pre-built `LcsPattern`.** PMV для каждого query-токена строится **один раз на нажатие «Поиск»** (на 1–4 query-токенах это микросекунды) и переиспользуется на всех 581k+167k+69k кандидатах. Тип:
   ```swift
   struct LcsPattern {
       let m: Int
       let pmv: [Unicode.Scalar: UInt64]
       let isLong: Bool                    // m > 64 → fallback на DP
       let fallback: [Unicode.Scalar]
   }
   ```

2. **Cutoff-pruning.** В `tokenMinRatio`, после обработки очередного query-токена, если `bestForQ < SCORE_CUTOFF`, итоговый `min(...)` гарантированно тоже будет < cutoff — return 0 досрочно, остальные query-токены не считаем. Сильно режет работу на многословных запросах против большинства кандидатов.

Замеры на реальном кэше (581k книг / 167k авторов / 69k серий, M-серия Apple Silicon, release-сборка `swiftc -O`):
- **наивная реализация** (PMV per-call): 2.2–3.3 с на запрос.
- **с pre-built PMV + cutoff pruning**: **400–440 мс на запрос**, **стабильно** на любой длине запроса (1, 2, 3, 4 токена). Обе категории и книги — суммарно. Корпус: 13/13 пройден.

Эталонный код спайка лежит в `~/code/fb-loader-search-spike/spike3.swift` (рядом с `librarium-py`, не внутри `fb-loader`-репы) — переиспользовать дословно при имплементации.

**Score cutoff = 75** (как в `librarium`). Эмпирически отделяет реальные матчи (80–100) от шума (≤66).

### Параллелизм

`DispatchQueue.concurrentPerform(iterations: cores)` поверх N равных чанков — отдельно для книг, отдельно для авторов, отдельно для серий. `LcsPattern[]` query-токенов разделяется между потоками без копирования (immutable), thread-safe by construction. Каждый поток набирает локальный top-K через insertion sort, в конце результаты мержатся.

Ради простоты — три последовательных параллельных скана (книги, потом авторы, потом серии). Перекрёстная параллелизация трёх категорий (например через `TaskGroup`) не нужна — они уже сатурируют ядра внутри книжного скана, который занимает 80%+ времени.

### Корпус-тесты скорера

Эталоны взяты из комментариев `librarium/search.py` + edge-кейсы. На спайке прошли 13/13:

- Положительные: склонения (`прошивка→прошивки`, `короли→королей`), префиксы (`достоевск→достоевский`), опечатки на 1 символ (`сандерсн→сандерсон`), ё/е (`ёлка→елка`), пунктуация (`Тайфун!→тайфуны`), регистр+пробелы, перестановка слов (`сандерсон брэндон→Брэндон Сандерсон`).
- Отрицательные: ложный LCS (`короли→космобиолухи`, `крыса→корсакова`), шумная подстрока (`мария→информация`), короткое-vs-короткое (`мария→марк`).
- Документированное ограничение: `толк→толкиен` отбрасывается (короткий префикс против длинного слова — ratio ниже cutoff).

Эти тесты переезжают в `FB LoaderTests` как regression suite.

## UI

### Поверхность

**Модальный sheet** `"Поиск по библиотеке"` поверх главного окна (`.sheet(isPresented:)` на `LeftSidebarView`). Изначально проектировалось как отдельная сцена `Window(id:)`, но в обсуждении выбрали sheet — он сильно проще: не нужно поднимать `AppState` на App-уровень, не нужны отдельные сцены, lifecycle-edge-кейсы (что делать, если каталог реимпортируется во время поиска) автоматически отпадают, потому что главное окно блокировано на время отображения sheet'а.

**Активация:** значок лупы (`Image(systemName: "magnifyingglass")`) в верхней области `LeftSidebarView`, рядом с пикером вкладок. Клик открывает sheet.

**Жизненный цикл:** без персиста состояния. SwiftUI `.sheet` пересоздаёт content View при каждом показе — это автоматически даёт «каждое открытие — чистое окно». Между запусками приложения тем более ничего не сохраняется. Закрытие — кнопка «Закрыть» в верхнем баре или клавиша Escape.

### Управляющие элементы (top bar)

- **Поле запроса** — `TextField`. Триггер поиска: только кнопка «Поиск» (или Enter в поле). На лету ничего не ищем.
- **Языковой пикер** — `LanguageFilterPicker`-копия. **Значение наследуется** от `state.languageFilter` при открытии окна, дальше живёт независимо в локальном стейте окна. Смена языка сбрасывает текущую выдачу — результаты разных языков не смешиваются.
- **Кнопка «Поиск»** — синхронный (для UX-логики) запрос: задизаблить поле и кнопку, показать прогресс/спиннер на ~400–500 мс, по завершении вывести результаты.

### Группы

Три фиксированных раздела, в порядке сверху вниз:

#### 1. Авторы

Все авторы со скорером ≥ 75 на матче `name`, у которых есть книги на выбранном языке, отсортированные по убыванию скорера. По умолчанию показывается **топ-10**, под последним — кнопка «Показать всех (N)». Клик раскрывает остаток в этой же сессии окна.

Под каждым автор-заголовком — **все** его книги, отфильтрованные по языку, организованные точно как в основной таблице при выборе этого автора (`BooksTableView:18-61`):
- сначала «одиночные» книги (без серии),
- затем под-секции по сериям (заголовок серии + счётчик), книги внутри серии — по `seriesNum`.
- порядок «одиночных» и серий — как в `BooksByContext.books(for: .author(...))`.

Без пагинации внутри группы — стоимость загрузки книг автора копеечная (массив уже в `Library.booksByAuthor[id]`).

Заголовок «автор &lt;имя&gt;» — кликабелен, **сворачивает/разворачивает** всю группу. По умолчанию — развёрнута.

#### 2. Серии

Все серии со скорером ≥ 75 на матче `name`, у которых есть книги на выбранном языке, отсортированные по убыванию скорера. По умолчанию топ-10 + «Показать все (N)».

Под каждой серия-заголовком — **все** книги серии, отфильтрованные по языку, отсортированные по `seriesNum`. Справа от заголовка — короткая контекстная строка (имя «основного» автора серии + счётчик «N книг»), как на референс-скрине.

Заголовок кликабелен, сворачивает/разворачивает группу. По умолчанию развёрнута.

#### 3. Совпадения по книгам

Книги, чьё совпадение прошло fuzzy по комбинированному ключу `title + author_name + series_name` (LIGHT-вариант: токены добираются на лету при сканировании). Сортировка — по убыванию скорера.

Пагинация: первые 20 + «Загрузить ещё +20». Шаг — 20.

### Строки книг

Те же колонки, что в `BookRow` основной таблицы: чекбокс, название, №-в-серии, размер, дата, жанры. Реюз компонента, в идеале — как самостоятельная View с инжектируемыми bindings вместо прямого `@Environment(AppState.self)`, чтобы корректно работать с локальным стейтом окна (см. ниже про чекбоксы).

**Клик по строке** — выделяет книгу и обновляет деталь в нижней панели **этого окна**. На `state.selectedBookLibid` основного окна не влияет.

### Деталь книги

Внизу окна — `BookDetailView` (тот же компонент, что в главном окне), показывает выбранную в результатах книгу. Если ничего не выбрано — placeholder «Выберите книгу».

### Чекбоксы и экспорт

**Окно поиска самодостаточно по чекбоксам и экспорту.** Локальный `Set<Int32>` checked libids живёт в стейте окна, в основной `state.checkedBookLibids` ничего не пишется. У окна — собственная кнопка «Экспорт» (или контекстное меню на строке), запускающая существующий `ExportPlanner`/`ExportRunner` со своими libids.

Это даёт чёткую изоляцию: пользователь работает в окне поиска как в самостоятельной выгрузке, не влияя на состояние главного окна. Закрытие окна сбрасывает локальные отметки (см. «без персиста»).

### Состояния

- **До первого поиска** — пустое тело, placeholder «Введите запрос и нажмите „Поиск“».
- **Идёт поиск** — поле и кнопка disabled, спиннер на месте результатов, отмена не предусмотрена (бюджет ~400–500 мс на типовом запросе укладывается в терпимое ожидание).
- **Ничего не найдено** — текст «По запросу „&lt;q&gt;“ ничего не найдено».
- **Индекс ещё строится** (теоретически невозможно при sync-build в Library.init, но подстраховка) — поле и кнопка disabled, текст «Индекс поиска готовится, подождите…».

Рефакторим: принимает `Binding<String>` явным параметром. Существующий вызов в `LeftSidebarView` и в окне поиска — оба передают своё binding (один — `$s.languageFilter`, второй — локальный `@State`).
- **`UI/BookDetail/BookDetailView`** — переиспользуем как есть. Параметры `library`/`archivesRoot`/`book` приходят из родителя; внутри использует `@Environment(AppState.self)` для второстепенных вещей (translator-state и т.п.), поиск не мешает. Но: в окне поиска «выбранная книга» — локальный `@State<Int32?>`, не `state.selectedBookLibid`.
- **Экспорт.** Реюзим `ExportPlanner.plan(...)` и `ExportRunner.run(...)` как есть. Окно поиска вызывает `ExportPlanner.plan(libids: localChecked, rootFolder: …, selectedAuthorID: nil, selectedSeriesID: nil, in: library)` — `nil`/`nil` означают «папки по первому автору каждой книги», что для микса книг из разных авторов/серий — естественное поведение.

## Что вне скоупа

- Пресет-сохранение запросов между запусками.
- Подсветка совпадений в строках результатов (highlighting подстроки запроса в тайтле/имени).
- История запросов.
- Триграммный/n-gram префильтр — не нужен, текущие ~420 мс с pre-built PMV комфортны. Архитектура его не блокирует, если когда-нибудь захочется on-type поиск.
- Параллельная индексация (build keys) — текущие 2 с сборки в `Library.init` сжать можно (чанками + concurrentPerform), но это оптимизация на потом.
- Транслит латиница↔кириллица — спайк показал, что запрос «azimov osnovanie» не находит «Азимов / Основание». Можно добавить как отдельную фичу позже.
- Менее строгий режим для авторов/серий при многословных запросах — сейчас «Сандерсон Эпантрис» в бакете «Авторы» даёт 0 (требует, чтобы все query-токены нашлись в имени). Это унаследовано из librarium и by-design; ослабление до «matches at least one query token» — на будущее.
- Локальные отметки окна → основная таблица. Окно умышленно изолировано.

## Открытые риски

1. **Память.** На реальном кэше LIGHT search-ключи дают ~+370 МБ RSS поверх ~165 МБ Library (по спайк-замерам). Замер не вполне стерильный — стоит подтвердить чистым прогоном после реализации. Если в проде это окажется ощутимо — есть очевидные точки экономии (хранить токены как один flat `[UInt32]` буфер с per-entity offset-таблицей), но в v1 не делаем.
2. **Корректность LCS на широком корпусе.** Корпус из 13 кейсов покрывает классы матчей, но не всё многообразие запросов. Будут «странные» матчи — настраиваем cutoff или докручиваем скорер; это уже tuning поверх ядра. Cross-check `DP ≡ BP` в спайке прошёл на всех парах токенов корпуса — алгоритмическая эквивалентность бит-парлельной реализации DP-эталону подтверждена.
3. **Cold-start UX.** +2 с к и так не моментальной загрузке `Library`. Решено показывать как часть стандартного лоадера; если в проде окажется «обидно» — рассмотрим персист в бинарном кэше (с bump формата) как fallback.
4. **Качество ранжирования на многословных запросах.** Спайк-проба показала: «Сандерсон Эпантрис» (typo в книге) находит правильные книги Сандерсона со скором 87.5. Но для бакета «Авторы» при многословном запросе семантика `tokenMinRatio` строгая (все query-токены должны найтись), что даёт 0 авторов на смешанном «автор + книга»-запросе. На UX-уровне выглядит ОК — пользователь увидит совпадения в бакете «Книги», — но если посыпятся жалобы, ослабляем семантику для бакетов авторов/серий отдельно.

## Acceptance criteria

- Кнопка-лупа в сайдбаре открывает модальный sheet «Поиск по библиотеке» поверх главного окна.
- В окне: поле, языковой пикер (наследует значение от главного окна, дальше независим), кнопка «Поиск».
- Триггер только по кнопке/Enter.
- Результаты группируются на: «Авторы» (топ-10 + «Показать всех»), «Серии» (топ-10 + «Показать все»), «Совпадения по книгам» (20 + «Загрузить ещё +20»).
- Заголовки авторов/серий кликом сворачивают/разворачивают свою группу. Все развёрнуты по умолчанию.
- Под автором — его книги в структуре основной таблицы (одиночные + по сериям с под-заголовками); под серией — её книги по `seriesNum`. Языковой фильтр окна применяется.
- Клик по строке книги → деталь в нижней панели окна. Главное окно не трогается.
- Чекбоксы локальные, кнопка «Экспорт» в окне работает с локальным набором отметок.
- 13/13 кейсов корпуса fuzzy-скорера зелёные.
- Cross-check `lcsLengthDP ≡ lcsLengthBP` зелёный на всех парах токенов корпуса.
- Время отклика на типовом запросе на каталоге ~580k книг — **≤500 мс** (замер в спайке: 400–440 мс стабильно при любой длине запроса).
- Cold-start: индексы поиска включены в шаги загрузки `Library`, прогресс отображается в существующем лоадере (`LoaderScreen` через `state.stage = .loading(progress:)`).
